캡처 가능 범위 정의

캡처 난이도 티어 T0–T4

웹사이트를 "애니메이션이 많다 / 적다"로 나누면 캡처 범위를 정할 수 없습니다. 캡처를 실패시키는 건 애니메이션의 화려함이 아니라 종류이기 때문입니다. 무엇이 우리 도구를 무너뜨리는지를 기준으로 5단계를 정의하고, 그 판정을 사람 눈이 아니라 브라우저 계측으로 하도록 만들었습니다.

  • 2026-08-27
  • 웹사이트 스냅샷 자동화
  • 분류기 자체 테스트 7/7 통과
진행 상태 — 실측 완료

이 분류 체계로 GDWEB 선정작 50곳을 실제로 계측했습니다. 결과는 「실측 결과」 문서에 있습니다 — 측정 49건, 실패 1건, v1 커버율 49%. 후속 30건까지 합치면 78건에 50%입니다.

그리고 그 실측이 이 분류기의 오류를 잡아냈습니다. 49건 중 21건이 과대 판정이었고, 원인은 셋 다 같았습니다 — 라이브러리가 "있다"는 사실을 그 라이브러리가 "무엇을 한다"와 혼동한 것. 규칙을 고쳐 회귀 테스트로 고정했습니다. 아래 티어 정의 자체는 그대로 유효하고, 바뀐 것은 판정 규칙입니다.

01

어떤 기준으로 나눴나

기준은 하나입니다 — "제대로 찍으려면 캡처 엔진이 무엇을 해야 하는가."

겉보기로 나누면 안 되는 이유가 있습니다. 스크롤하면 요소가 스르륵 나타나는 사이트와 스크롤에 맞춰 화면이 재생되는 사이트는 보는 사람 눈에는 둘 다 "스크롤 애니메이션"이지만, 캡처 난이도는 정반대입니다. 앞의 것은 끝 상태가 정해져 있어서 그 상태로 건너뛰고 찍으면 그만이고, 뒤의 것은 스크롤 위치가 곧 재생 시점이라 "이 페이지의 올바른 전체 이미지"라는 게 애초에 존재하지 않습니다.

그래서 티어를 가르는 질문은 "애니메이션에 끝이 있는가, 있다면 그 끝을 우리가 만들 수 있는가"입니다.

02

다섯 단계

티어는 가장 높은 신호를 따릅니다. 등장 애니메이션과 WebGL 배경이 함께 있으면 T4입니다. 파이프라인이 감당해야 할 난이도는 가장 어려운 요소가 결정하기 때문입니다.

T0

정적 — 그냥 찍으면 된다

v1 커버
정의
스크롤만 끝까지 내리면 모든 콘텐츠가 보입니다. 움직이는 것이 없거나, 있어도 장식 수준입니다.
대표
기업 소개, 공공기관, 병원·학교, 관리자 화면, 문서형 페이지
대응
추가 처리 없이 풀페이지 캡처. 고정 헤더만 숨기면 끝입니다.
주의
여기서도 페이지가 길면 잘립니다. 티어와 무관하게 붙는 L 태그를 보세요.
T1

등장형 — 스크롤하면 나타난다

v1 커버
정의
요소가 처음엔 투명하거나 아래로 밀려 있다가, 화면에 들어오면 제자리로 옵니다. 이미지는 필요할 때 로드됩니다. 끝 상태가 명확히 하나입니다.
대표
요즘 브랜드 사이트 대부분. AOS·ScrollReveal, IntersectionObserver 기반 페이드인, loading="lazy" 이미지
대응
끝까지 천천히 스크롤해 전부 발동시킨 뒤, 브라우저가 유한 애니메이션을 완료 시점으로 빨리감기 하게 만듭니다. 기획안 기능 1이 정확히 겨냥한 지점이고, 이미 표준 기능입니다.
검증
스크롤 전후로 "등장 대기 요소" 수를 세면 실제로 해소됐는지 확인됩니다. 남아 있으면 캡처가 이른 것입니다.
T2

순환형 — 계속 움직인다

조건부 커버
정의
끝나지 않고 반복됩니다. 정지할 "완료 상태"가 없습니다.
대표
자동 넘어가는 캐러셀, 흐르는 텍스트(마퀴), 루프 배경 영상, 반짝이는 배지, 파티클 장식
대응
무한 애니메이션은 초기 상태로 되돌린 뒤 찍고 다시 재생시킵니다(브라우저 자동화의 기본 동작). 영상은 첫 프레임이나 포스터로 고정합니다.
진짜 문제
결과가 매번 달라진다는 점입니다. 틀린 프레임은 없지만 정답 프레임도 없어서, 기능 2의 AI 검수가 "달라졌다 = 잘못됐다"로 오판하기 쉽습니다. 순환 영역을 검수 대상에서 빼거나 별도 기준을 두어야 합니다.
T3

스크롤 연동형 — 스크롤이 곧 타임라인

별도 모드 필요
정의
스크롤을 내리는 만큼 애니메이션이 재생됩니다. 화면은 고정된 채(pin) 내용만 바뀌거나, 세로 스크롤이 가로 이동으로 변환됩니다.
대표
GSAP ScrollTrigger 핀 섹션, 스크롤리텔링, 가로 스크롤 갤러리, Lenis·Locomotive 스무스 스크롤
왜 다른가
여기서는 "풀페이지 캡처"라는 개념 자체가 성립하지 않습니다. 문서 높이는 스크롤 길이를 만들려고 부풀린 값이라 실제 콘텐츠 양과 무관합니다. 이어 붙이면 같은 섹션이 여러 번 나오거나 중간 상태만 남습니다. 기존 캡처 도구가 이 사이트들에서 무너지는 진짜 이유입니다.
대응
문제를 다시 정의해야 합니다 — 한 장이 아니라 "스크롤 구간별 스냅샷 시퀀스". 이건 기능 1의 개선이 아니라 별개 모드입니다.
권고
v1 범위에서 빼고, 감지되면 사용자에게 알리는 것을 권합니다. 조용히 이상한 결과를 내는 것보다 낫습니다.
T4

실시간 렌더형 — 매 프레임 다시 그린다

범위 밖
정의
화면이 HTML 요소가 아니라 <canvas>에 매 프레임 새로 그려집니다. 3D, 셰이더, 물리 시뮬레이션.
대표
three.js·Spline 3D 히어로, WebGL 셰이더 배경, 마우스를 따라다니는 파티클, 물리 인터랙션
왜 안 되나
애니메이션 정지 기능은 CSS 애니메이션과 Web Animations만 멈춥니다. 코드가 직접 캔버스에 그리는 것은 멈추지 않습니다. 게다가 "다 그려졌다"는 시점이 원리적으로 존재하지 않습니다 — 계속 그리는 게 정상 동작이니까요.
결과
같은 URL을 두 번 찍으면 다른 이미지가 나옵니다. 결정론적 캡처가 불가능합니다. 재캡처 로직에 넣으면 영원히 수렴하지 않습니다.
03

티어와 별개로 붙는 태그

난이도와 직교하는 조건들입니다. T0 정적 페이지에도 붙을 수 있고, 붙으면 그 자체로 캡처를 망칩니다. 티어에 섞지 않고 따로 두는 이유입니다.

직교 태그
태그무엇캡처에 미치는 영향대응
G Gated 봇 차단 화면, 로그인 벽, 나이 확인 페이지 자체를 못 봅니다. 검수가 "로딩 실패"로 오인해 재캡처를 반복하면 차단이 더 강해집니다. 별도 상태로 분리하고 재캡처하지 않습니다
S Sticky 고정 헤더, 플로팅 버튼, 하단 배너 나눠 찍어 이어 붙일 때 화면마다 따라와 여러 번 겹쳐 나옵니다 촬영 직전 일시 숨김
L Long 문서 높이가 브라우저 한계에 근접 16,384px를 넘으면 잘립니다. 2배율로 찍으면 절반 길이에서 잘립니다 슬라이스 분할 + 배율 자동 강등
H Hidden 호버·클릭해야 보이는 메가메뉴, 탭, 아코디언 그냥 찍으면 콘텐츠가 통째로 빠집니다 알려진 패턴만 미리 열기(v1은 제한적)
읽는 법

예를 들어 T1 · S L은 "등장 애니메이션이 있고, 고정 헤더가 있고, 페이지가 아주 길다"는 뜻입니다. 셋 다 우리가 이미 대응 가능한 조합이므로 v1에서 문제없이 찍힙니다.

반면 T3 · G는 스크롤 연동형인데 봇 차단까지 걸린 사이트 — v1에서는 손대지 않는 것이 맞습니다.

04

판정은 눈이 아니라 계측으로

사람이 보고 "이건 T3 같다"고 정하면 사이트 60개를 일관되게 분류할 수 없습니다. 그래서 페이지 안에서 실제로 셀 수 있는 신호만 쓰도록 스캐너를 만들었습니다. 계측 코드는 페이지 스크립트보다 먼저 심어 라이브러리 호출을 가로챕니다.

분류기가 실제로 맞는지 확인했습니다

각 티어를 대표하는 테스트 페이지와 실전 오분류 사례를 픽스처로 만들어 스캐너에 물렸습니다. 규칙을 고칠 때 회귀를 잡아 주는 자동 테스트로 고정해 두었습니다.

ok t0-static.html T0 특별한 동적 신호 없음 ok t1-reveal.html T1 지연 로딩 이미지 2개 / 등장 대기 요소 4개 / IntersectionObserver 3회 생성 ok t2-loop.html T2 무한 반복 애니메이션 2개 / infinite 키프레임 규칙 2건 / 자동재생·루프 비디오 1개 ok t3-scrolllinked.html T3 핀 고정 섹션 1개 / 가로 스크롤 섹션 1개 ok t4-webgl.html T4 WebGL 컨텍스트 1개 / 유휴 상태에서도 rAF 59회/초 + 대형 canvas ok gated.html 차단(challenge) 특별한 동적 신호 없음 7/7 통과
만들면서 잡은 실제 버그

첫 실행에서 T2 페이지가 T3로 잘못 분류됐습니다. 원인은 body { overflow-x: hidden }을 "스크롤 탈취"로 오인한 것이었습니다. 이 선언은 가로 스크롤바를 없애려고 거의 모든 사이트가 쓰는 관용구라, 그대로 뒀다면 실측에서 평범한 사이트가 무더기로 T3로 분류됐을 것입니다.

지금은 세로축이 잠겨 있고, 문서 자체가 스크롤되지 않으며, 내부에 진짜 스크롤 컨테이너가 있을 때 — 세 조건을 모두 만족할 때만 스크롤 탈취로 인정합니다. 판정 근거를 전부 기록해 두었기 때문에 잡을 수 있었던 버그입니다.

모든 결과에는 사람이 읽는 reasons와 원 신호 evidence가 함께 저장됩니다. 분류가 이상해 보이면 신호를 직접 열어 규칙을 고칠 수 있습니다 — "AI가 그렇다더라"로 끝나는 결과는 만들지 않는다는 것이 이 도구의 설계 원칙입니다.

05

다시 돌리려면

스캐너는 tools/gdweb-scan/에 있습니다. GDWEB 목록 URL을 주면 상세 페이지를 따라가 수상 사이트의 실제 주소를 뽑고, 한 곳씩 열어 분류합니다.

$ cd tools/gdweb-scan && npm install $ npm run scan -- --list "<GDWEB 목록 URL>" --pages 1-3 --limit 60 --concurrency 4 목록 1쪽 → 누적 60건 상세 페이지 60건에서 사이트 URL 추출 중… [1/60] T1 https://... [2/60] T3 https://... [3/60] 차단(challenge) https://... → results.json (원 신호 + 판정 근거) → report.html (사람이 읽는 분류 결과)

이미 한 번 돌렸습니다

  1. 2026-08-27, 사내 맥에서 50건 실행. 결과는 「실측 결과」 문서와 저장소의 docs/research/results.gdweb-2026.csv에 있습니다.
  2. 분류기를 고친 뒤에는 다시 돌려야 합니다. 「실측 결과」의 수치는 기록된 판정 근거로 재계산한 값이라, 수정된 규칙으로 새로 스캔하면 확정됩니다.
  3. 대상을 바꿔 돌려도 됩니다. urls.gdweb-2026.txt를 열어 고객사 사이트로 바꾸면 훨씬 현실적인 커버율이 나옵니다 — 어워드 수상작은 난이도 상한선이니까요.

실측 결과가 나오면 알 수 있는 것

  • v1 커버율 — T0+T1+T2 비중이 곧 "지금 설계로 찍을 수 있는 사이트 비율"입니다.
  • T3 비중 — 이 숫자가 크면 스크롤 시퀀스 모드를 v1으로 당겨야 한다는 뜻입니다. 작으면 예외 처리로 충분합니다.
  • G 태그 비중 — 봇 차단 대응에 돈을 쓸 필요가 있는지를 결정합니다.
  • L 태그 비중 — 슬라이스 분할이 예외인지 기본값인지를 결정합니다.
표본에 대한 주의

GDWEB 선정작은 디자인 어워드 수상작이라 인터랙션이 평균보다 훨씬 화려합니다. 여기서 나온 T3·T4 비중은 웹 전체의 분포가 아니라 상한선으로 읽어야 합니다. 팀이 실제로 캡처하는 대상(고객사 사이트, 경쟁사 랜딩)은 이보다 쉬울 가능성이 높습니다.

거꾸로 말하면 가장 어려운 표본으로 먼저 테스트하는 셈이라, 도구의 한계를 빨리 드러내는 데는 좋은 선택입니다.
