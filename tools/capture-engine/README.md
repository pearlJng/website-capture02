# capture-engine — 캡처 파이프라인과 결정성 채점기

스캐너(`../gdweb-scan`)가 "이 사이트가 얼마나 어려운가"를 재는 도구라면,
여기는 **"우리가 실제로 몇 %를 제대로 찍는가"**를 재는 도구입니다.

## 왜 채점기부터인가

캡처 품질을 사람이 눈으로 검수하면 규모가 안 나옵니다. 다행히 안 해도 됩니다 —
T0~T4 티어 정의가 그대로 채점 기준이기 때문입니다.

> **같은 사이트를 두 번 찍어서 픽셀이 같으면 성공, 다르면 실패.**

T0~T2 는 두 번 찍어 같아야 정상이고, T4 는 원리적으로 같을 수 없습니다.
스캔 결과 CSV 가 정답지 역할을 하므로, 엔진을 고칠 때마다 성적이 바로 나옵니다.

### 결정성만으로는 부족합니다

두 번 다 **똑같이** 실패하면 픽셀은 같습니다. 스무스 스크롤 사이트에서 실제로
그 일이 납니다 — 끝까지 스크롤하지 못한 채 짧게 찍히고, 두 번 다 그러니 "통과"로
보입니다. 그래서 **완주** 검사를 따로 둡니다:

- **미완주** — 문서가 화면보다 긴데 스크롤이 바닥에 닿지 못했다 (가장 확실한 신호)
- **짧음** — 스캐너가 잰 문서 높이의 90% 에 못 미친다
- **미확인** — 스크롤을 가로채는 라이브러리를 발견했는데 걷어내지 않고 찍었다

둘 다 통과해야 통과입니다.

## 단계

파이프라인의 각 단계는 껐다 켤 수 있습니다. 무엇을 켰을 때 성적이 얼마나 오르는지
재기 위해서입니다. 단계 목록은 78건 실측이 정했습니다.

| 단계 | 하는 일 | 실측 근거 |
|---|---|---|
| `sticky` | 플로팅 요소를 숨기고 헤더 하나는 남긴다 | 고정 요소 100% |
| `motion` | Lenis·Locomotive 를 걷어내 네이티브 스크롤을 돌려준다 | 스무스 스크롤 27% |
| `anim` | Swiper 자동재생·GSAP 무한 트윈·비디오·CSS 루프를 멈춘다 | 라이브러리 4개가 절반 |
| `slice` | 긴 문서를 여러 장으로 나눠 찍는다 | 초장문 |

`--steps none` 이 baseline(지금 설계)입니다. 여기서 시작해 한 단계씩 켭니다.

## 어떤 브라우저로 찍는가 — 설치된 크롬을 먼저 씁니다

Playwright 가 들고 다니는 크로미움은 **오픈소스 빌드**라 **H.264(MP4)와 AAC
코덱이 없습니다.** 특허가 걸려 있어 구글이 라이선스를 사서 브랜드 크롬에만
넣기 때문입니다.

그래서 그 크로미움으로 유튜브 임베드나 MP4 비디오가 있는 페이지를 열면
플레이어가 "재생할 수 없음" 오류 화면을 띄우고, 캡처에는 그 오류가 그대로
박힙니다. GoFullPage 같은 확장이 멀쩡한 이유는 사용자가 쓰는 **진짜 크롬**
안에서 돌기 때문입니다.

그래서 이 도구는 **설치된 크롬 → 엣지 → 번들 크로미움** 순으로 찾습니다.
크롬이 없으면 실행할 때 경고하고, 보고서와 `목록.html` 에도 표시합니다.

`node doctor.mjs` 로 이 컴퓨터가 어떤 코덱을 쓸 수 있는지 볼 수 있습니다.

## 어떻게 찍는가 — 화면 단위로 찍어 이어 붙입니다

이게 이 도구에서 가장 중요한 선택입니다.

**한 방에 풀페이지로 찍으면 안 됩니다.** 브라우저가 문서 전체를 한 번에
그리는데, 그때 화면 밖 콘텐츠는 "화면 밖" 상태입니다. 등장 애니메이션
대부분이 들어올 때 클래스를 붙이고 **나갈 때 떼기** 때문에, 맨 아래까지
훑고 맨 위로 돌아와 찍으면 아래쪽이 전부 다시 투명해진 채로 찍힙니다.
실측 픽스처에서 6칸 중 5칸이 그랬습니다.

그래서 **각 칸이 화면에 있는 동안 그 화면을 찍고, 이어 붙입니다.**
GoFullPage 같은 확장이 멀쩡한 이유가 이것입니다. 두 번째 조각부터는
따라붙는 고정 요소를 숨겨서 헤더가 조각마다 반복되지 않게 합니다.

`--mode fullpage` 로 예전 방식도 쓸 수 있습니다 — 빠르지만 위 경우 아래가 빕니다.

## 실제로 쓰는 도구 — shoot.mjs

채점기가 "몇 %를 제대로 찍나"를 재는 도구라면, 이건 **스크린샷을 내놓는 도구**입니다.

```bash
node shoot.mjs --file ../gdweb-scan/urls.imweb10.txt --out ./결과
node shoot.mjs --urls https://example.com --out ./결과 --scale 2
```

다른 캡처 도구와 다른 점은 하나입니다 — **찍고 나서 스스로 검사합니다.**
같은 페이지를 두 번 찍어 픽셀이 다르면 아직 뭔가 움직인다는 뜻이므로 다시
찍습니다. 그래도 다르면 `검수 필요`로 표시하고 무엇이 달랐는지
`<이름>__차이.png` 로 남깁니다.

결과 폴더에 이렇게 생깁니다.

| 파일 | |
|---|---|
| `<사이트 이름>.png` | 스크린샷 |
| `<사이트 이름>__차이.png` | 두 번이 달랐을 때만. 1차 / 2차 / 차이 마스크 |
| `목록.html` | 전체를 한눈에 넘겨보는 페이지. 브라우저로 여세요 |
| `보고서.txt` · `목록.csv` | 상태 요약 |

## 채점기 — score.mjs

```bash
npm install

# 1. 베이스라인 — 아무것도 안 고친 상태의 성적
node score.mjs --from ../gdweb-scan/results.gdweb-2026-v2.csv --steps none

# 2. 단계를 하나씩 켜면서 기여도 측정
node score.mjs --from ../gdweb-scan/results.gdweb-2026-v2.csv --steps sticky
node score.mjs --from ../gdweb-scan/results.gdweb-2026-v2.csv --steps sticky,motion

# 3. 전부 켠 성적 = v1 커버율 실제값
node score.mjs --from ../gdweb-scan/results.gdweb-2026-v2.csv --steps all

# 2배율, 결과 PNG 도 남기기
node score.mjs --from ../gdweb-scan/results.tier30.csv --steps all --scale 2 --keep-shots ./shots
```

한 건당 두 번 찍으므로 스캔보다 두 배 이상 걸립니다. 50건이면 15~25분 정도 잡으세요.
`--concurrency` 기본값은 2 입니다.

## 차이가 나면 어디가 다른지 짚어 줍니다

`--keep-shots` 를 주면 실패한 건마다 **다른 구간만 잘라 붙인 그림** 한 장이
같이 남습니다 (`<이름>__차이.png`) — 위에서부터 1차 / 2차 / 차이 마스크입니다.

```
차이 y 1,342~1,382px · 가로 200~320px · 한 덩어리
```

보고서와 CSV 에도 같은 좌표가 들어갑니다. **덩어리 수가 1이면 원인도 하나**일
가능성이 높습니다. 0.01% 짜리 차이를 찾겠다고 9,000px 짜리 그림 두 장을
눈으로 훑을 필요가 없습니다.

## 회귀 테스트

```bash
npm test
```

브라우저가 통째로 죽으면 한 번 다시 띄우고 재시도합니다. 그래도 계속 죽으면
환경 문제이므로 아래 진단을 돌려 보세요.

## 환경 진단

```bash
node doctor.mjs
```

30초쯤 걸립니다. 빈 페이지부터 긴 문서·애니메이션·캔버스·WebGL·2배율까지
하나씩 찍어 보고, 이 컴퓨터의 크로미움을 넘어뜨리는 게 무엇인지 짚어 줍니다.
자체 테스트가 "캡처 실패"로 끝났을 때 원인이 특정 픽스처인지 환경 전체인지
가르는 용도입니다.

`fixtures/` 의 페이지들은 실측이 지목한 문제를 하나씩 재현합니다.
"단계를 켜기 전에는 실패하고, 켜면 통과한다"를 검사합니다 — 단계가 진짜로
일을 하는지 확인하지 않으면 성적표를 믿을 수 없습니다.

## 실측으로 확인한 것 — 16,384px 은 캡처 한계가 아닙니다

이 저장소의 이전 문서는 "크롬 텍스처 한계 16,384px 을 넘으면 잘린다"고 적었는데,
**직접 재보니 사실이 아니었습니다.** Playwright/Chromium 이 내부에서 이어붙입니다.

| 실픽셀 높이 | 결과 |
|---|---|
| 102,578px (2배율, 문서 51,289px) | 성공 · 32.2초 |
| 205,124px (2배율, 문서 102,562px) | 실패 · `Unable to capture screenshot` |

진짜 제약은 **잘림이 아니라 시간과 메모리**이고, 한계선은 16,384px 이 아니라
실픽셀 10만~20만px 사이에 있습니다. 그래서 `slice` 단계는 여전히 필요하지만
이유가 다릅니다 — 잘리지 않게 하려는 게 아니라 **캡처 시간을 예측 가능하게**
묶어두기 위해서입니다. `SAFE_PIXELS = 30000` 이 그 상한입니다.

측정 환경은 이 저장소의 리눅스 컨테이너, Playwright 1.56.1, 가벼운 합성 페이지입니다.
사진이 많은 실제 페이지는 픽셀당 더 무거우므로 한계선이 더 낮을 수 있습니다.
맥에서 처음 돌릴 때 한 번 확인해 보시는 게 좋습니다.

## 브라우저 화면 — app.mjs

```bash
node app.mjs            # http://127.0.0.1:8890 이 열린다
```

주소 → 정보구조(GNB 트리, 체크로 고르기) → 화면 크기(1440/1920/375) → 전부 캡처 → IMG 폴더 / PDF 한 권으로 출력.
내 맥에서 돌리면 출력할 때 맥의 "별도 저장" 창이 뜬다.

## 서버에 올려 어디서든 주소로 쓰기

앱은 크롬을 띄워 찍는 프로그램이라 **크롬이 돌 수 있는 서버**가 필요하다. Dockerfile 이 그 그릇이다
(Playwright 공식 이미지 + 브랜드 크롬 — 번들 크로미움과 달리 H.264 동영상이 멀쩡히 찍힌다).

```bash
docker build -t snapshot .
docker run -d -p 8890:8890 -e APP_PASSWORD='원하는비밀번호' -v $PWD/결과:/app/결과 --shm-size=1g snapshot
```

- 메모리 **2GB 이상** (크롬이 페이지 두 개를 동시에 연다). `--shm-size=1g` 를 빼면 큰 페이지에서 크롬이 죽는다.
- `APP_PASSWORD` 를 꼭 건다. 아무나 남의 사이트를 캡처하게 두면 안 된다. 처음 들어갈 때 비밀번호를 넣으면 한 달 동안 기억한다.
- 서버에서는 맥 저장 창 대신 **브라우저 내려받기**로 나온다 — PDF 는 그대로, IMG 는 zip(풀면 폴더).
- Fly.io / Railway / Render 같은 곳은 Dockerfile 을 그대로 읽는다. 환경변수에 `APP_PASSWORD` 를 넣고, 메모리를 2GB 로 잡으면 된다.
  결과 파일을 남기려면 `/app/결과` 에 볼륨을 붙인다.

같은 사무실 안에서만 쓸 거면 서버 없이도 된다. 맥에서 `node app.mjs --host 0.0.0.0 --password 비밀번호` 로 띄우고
`http://<그 맥의 IP>:8890/` 으로 들어가면 된다 (그 맥이 켜져 있는 동안).

## 파일

| 파일 | 역할 |
|---|---|
| `capture.mjs` | 파이프라인. 열기 → 모션 해제 → 완주 스크롤 → 정지 → 고정 요소 정리 → 찍기 |
| `diff.mjs` | 두 캡처 비교. 통과하는 경우는 바이트 비교로 끝나고, 다를 때만 픽셀을 펼친다 |
| `score.mjs` | CLI. 두 번 찍고 채점해 보고서와 CSV 를 낸다 |
| `browser.mjs` | 브라우저가 죽으면 다시 띄우는 호스트. 긴 실행이 한 번의 크래시로 날아가지 않게 한다 |
| `selftest.mjs` | 회귀 테스트 |
| `doctor.mjs` | 환경 진단 |
| `fixtures/` | 문제 상황을 하나씩 재현한 페이지들 |
